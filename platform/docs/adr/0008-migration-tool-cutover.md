# ADR 0008 — Real migration tracking: Supabase CLI adoption for the 157-file pile

- **Status:** Proposed — tooling + baseline files built and syntax-verified; **marking the
  baseline "applied" against prod is NOT done (gated, needs Jeff's go)**.
- **Date:** 2026-07-28
- **Decision driver:** platform-hardening queue, phase 1 item 6 / `docs/TEAM-READINESS.md`
  Phase C — "Replace hand-run `.sql` files with a real migration tool (schema-in-code,
  up/down, applied-state tracking)."
- **Deciders:** Jeff (owner)
- **Author:** platform-hardening lane (phase 1 item 6)

---

## The problem (confirmed)

`platform/src/lib/migrations/` holds 156 hand-run `.sql` files (+ 1 more added
2026-07-28: `2026_07_28_rls_gap_closure_post_july15.sql`, = 157) plus one stray
already-CLI-formatted file in `platform/supabase/migrations/`
(`20260722145537_management_applications_resume_optional.sql`) = **158 files
total**, none of them tracked. Per `docs/runbooks/migration-runbook.md`, every
one was applied to prod by hand via the Supabase Management API, one at a
time, after Jeff's per-migration approval. There is no table, file, or tool
anywhere that records which of the 158 have actually landed on prod — the
runbook is a procedure, not a ledger.

This is exactly the gap ADR 0007 (staging environment) flagged as blocking a
reproducible local target, and the same gap `docs/TEAM-READINESS.md` Phase C
names directly.

## Decision

**Adopt the Supabase CLI's native migration system** (`supabase migration
new`, `supabase db push`, tracked via the `supabase_migrations.schema_migrations`
table Postgres extension the CLI manages). This is the vendor-native tool for
this exact stack — no third-party migration framework needed, no schema DSL
to learn, and it composes directly with the local Docker staging environment
ADR 0007 already scaffolded (`supabase/config.toml`, `supabase start`).

### What already existed (found, not assumed)

A prior pass (ADR 0007, same day) had already run `supabase init` at the repo
root: `supabase/config.toml` + `supabase/.gitignore` exist, `project_id =
"fullloopcrm-staging"`, Postgres `major_version = 17` (matches prod). It also
left `supabase/.temp/project-ref` pointing at prod's real project ref
(`cetnrttgtoajzjacfbhe`) — i.e. **the CLI in this environment is already
linked to prod**, not a scratch/staging project. No `.env` credential was
supplied to me for a DR-drill scratch project, so all verification in this
pass used the CLI's existing prod link for **read-only** checks only (see
Verification below) — nothing was written.

### What was built this pass

| File | Purpose |
|---|---|
| `platform/scripts/migrate-legacy-to-cli.mjs` | Idempotent, re-runnable converter. Reads the 158 legacy files, orders them by real git-history add-date (not filename — the pile mixes a numeric era `NNN_*.sql` and a dated era `YYYY_MM_DD_*.sql` that don't sort correctly against each other), and writes each into `supabase/migrations/<timestamp>_<slug>.sql` with a provenance header. Writes files only — touches no database. |
| `supabase/migrations/*.sql` (158 files) | The converted baseline, generated by running the script above. 157 are the pre-2026-07-28 pile (assumed already live in prod). 1 (`20260728194629_rls_gap_closure_post_july15.sql`) is today's new RLS work — deliberately kept separate, see below. |
| `supabase/BASELINE_VERSIONS.txt` | The 157 baseline version numbers + the exact `supabase migration repair` invocation to mark them applied, plus the gate/approval note. Not executed. |
| `docs/runbooks/migration-runbook.md` | New top section: the CLI-based workflow going forward, cross-referenced against the still-accurate prod-apply gate rules (unchanged — a prod write is a prod write regardless of which tool authored the SQL). |
| `platform/src/lib/migrations/README.md` | Marks the legacy directory **frozen** as of 2026-07-28 — historical record only, no new files. Points at `supabase/migrations/`. |

### The end-to-end proof: today's RLS migration through the new tool

Per the queue item's own instruction ("you're about to write new RLS policies
as migrations; don't add them to the unmanaged pile you're simultaneously
trying to eliminate"), `2026_07_28_rls_gap_closure_post_july15.sql` (209
lines, 26 RLS policies, file-only / not yet applied per its own commit
message) was converted into
`supabase/migrations/20260728194629_rls_gap_closure_post_july15.sql` — the
**first migration to go through the new tool** rather than the old pile.
It is deliberately **excluded** from the baseline-applied set: it stays
`PENDING` in the CLI's eyes, exactly matching its real state (not yet run on
prod). The moment Jeff approves it, `supabase db push` is the command that
applies it — no Management API curl call needed anymore.

## Verification (honest status)

**What I actually ran and what it proved:**

- `node --check platform/scripts/migrate-legacy-to-cli.mjs` — syntax valid.
- `node platform/scripts/migrate-legacy-to-cli.mjs --dry-run` then for real —
  produced 158 files, 157 baseline + 1 new, matching the source pile's file
  count exactly (verified by `ls | wc -l` before/after).
- `supabase migration list` — **this connected to the already-linked prod
  project** (read-only; the CLI's own comparison command, does not write).
  Output: **every one of the 157 baseline files shows `Remote` blank** (not
  yet recorded as applied in prod's tracking table — expected, since they
  were applied via raw Management API SQL execution, which does not touch
  `supabase_migrations.schema_migrations`). One unexplained finding:
  **`Remote` already has a single orphaned row, `20260727160000`, with no
  matching `Local` file** — something inserted a tracking-table row on
  2026-07-27 with no corresponding migration file in this repo. This
  predates today's work and is not something I created. **Flagging for Jeff
  before the baseline repair runs** — it should be understood (a previous
  worker's abandoned attempt at this same task? a manual `supabase migration
  repair` test?) before adding 157 more rows next to it.
- Did **not** run `supabase db push`, `supabase migration repair`, `supabase
  link`, or any other write command against prod. Did not have Docker
  available (`docker info` fails, same as ADR 0007 found), so could not spin
  up a local stack to verify against a disposable target instead. Was not
  given DR-drill scratch project credentials in this session and did not
  block on requesting them, per the task's "work entirely locally if the
  tool supports a dry-run/local check" fallback — the dry-run/file-generation
  path above is exactly that fallback.

**What is NOT verified:**

- Whether `supabase migration repair --status applied <157 versions>` will
  actually succeed cleanly against prod (e.g. no name/hash validation quirk,
  no interaction with the orphaned `20260727160000` row).
- Whether `supabase db push` on the new pending migration reproduces the
  exact same schema effect the Management-API-run original would have (the
  SQL body is byte-identical to the original file, only a comment header was
  prepended, so this risk is low but unexecuted).
- The full 158-file replay was not run against a fresh empty Postgres either
  (blocked on the same missing-Docker constraint ADR 0007 hit).

## Consequences

**If adopted:** every future migration is authored with `supabase migration
new <name>`, reviewed as a file exactly like today (peer review + PRE/POST
assertions per `migration-runbook.md`, unchanged), and applied with `supabase
db push` instead of a Management API curl call — same Jeff-approval gate,
less error-prone apply mechanism, and `supabase migration list` becomes the
single source of truth for "did it land" instead of institutional memory.

**Remaining steps to fully cut over (in order):**

1. **Jeff/leader: explain the orphaned `20260727160000` row** in prod's
   `supabase_migrations.schema_migrations` before proceeding — don't repair
   over an unknown state.
2. **Jeff's go, then LEADER runs** (same gate class as any other prod DB
   write, per `migration-runbook.md`):
   `supabase migration repair --status applied $(cat supabase/BASELINE_VERSIONS.txt | tail -1)`
   — marks the 157 baseline files applied without re-running any DDL.
3. **Verify**: re-run `supabase migration list` — all 157 should show
   matching `Local`/`Remote` timestamps; only
   `20260728194629_rls_gap_closure_post_july15.sql` should show `Remote`
   blank (still pending).
4. **Jeff's go, then LEADER runs** `supabase db push` to apply the RLS
   gap-closure migration for real (this is the same approval this file
   already needed under the old process — the tool changes, the gate
   doesn't).
5. Going forward: delete this "remaining steps" section once step 4 lands,
   and treat `docs/runbooks/migration-runbook.md`'s new top section as the
   only process doc.

Phase C (the checklist item this closes the tooling half of),

## 2026-08-01 addendum — reality check on "the 158 files question" (sec-08)

Re-audited this ADR against the actual repo state, prompted by the readiness
ledger's own sec-08 checkpoint (named exactly "the 158 files question").
Findings below are corrections/additions to the record above, not a redo of
the decision. **Status stays Proposed — nothing in this addendum applies the
baseline against prod; that remains gated on Jeff's go, same as before.**

### Correction: the 158-file baseline conversion IS real and committed

The original ADR text above is easy to misread as describing work that only
ever happened locally in one worker's session. Checked directly: commit
`6db15574a` ("feat: item 6 - real Supabase CLI migration tooling, replacing
214 hand-run SQL files", 2026-07-28) really did commit the converted files to
`supabase/migrations/` at the **repo root**, and that commit is a real
ancestor of this branch's HEAD (`git merge-base --is-ancestor` confirmed).
The directory holds 163 files as of this addendum (158 baseline + a few
genuinely-new native migrations authored directly through the CLI workflow
since, exactly as this ADR intended going forward, + the 1 recovered file
below). **This part of "the 158 files question" is settled: yes, they were
committed, and the count has kept growing correctly since.**

### New finding: a second, disconnected Supabase CLI project

`platform/supabase/` (note: **inside** `platform/`, not the repo-root
`supabase/` this ADR describes) is a **separate, accidentally-created local
Supabase CLI project** — `project_id = "platform"` (the directory-name
default, not the deliberate `fullloopcrm-staging` this ADR's "What already
existed" section names), and critically, it has **no
`supabase/.temp/project-ref`** — it has never been `supabase link`-ed to
prod at all. It was created by commit `47bc4acf8` (2026-07-29, an unrelated
tenant-profile feature commit) — almost certainly a worker running a
Supabase CLI command from inside `platform/` (this whole readiness effort's
own working-directory convention) without realizing a real, already-linked
`supabase/` project existed one level up at the repo root.

**This silently swallowed a real migration.** sec-06's RLS deny-all policy
migration (`docs/security/rls-policy-review-2026-07-30.md`,
`platform/supabase/migrations/20260730190000_explicit_deny_all_rls_policies.sql`)
was authored into this wrong, unlinked directory and was never picked up by
`scripts/migrate-legacy-to-cli.mjs` (its `STRAY_CLI_DIR` constant only knew
about `platform/supabase/migrations/`, but the script's *output* goes to the
repo-root `supabase/migrations/` — the file sat converted-nowhere in
between). Confirmed via `git ls-files` that the real, prod-linked baseline
never contained this file. Independently confirmed via sec-06's own
2026-07-31 `live_http_check` evidence that the policies this file defines
**are** genuinely active in prod (real anon-key PostgREST requests against
`tenants`/`platform_settings`/`security_events` correctly returned empty
results against non-empty tables) — so converting it into the real baseline
as "already live" is accurate, not a guess. **Fixed**: manually
added `supabase/migrations/20260730191108_20260730190000_explicit_deny_all_rls_policies.sql`
to the real, prod-linked baseline directory (content byte-identical to the
stray file, same header convention the conversion script uses) and included
its version in the regenerated `supabase/BASELINE_VERSIONS.txt` below.

**Resolved 2026-08-01 (W9 follow-up pass)**: the stray `platform/supabase/`
directory itself has now been **deleted**. Audit before deletion (grepped
the whole repo — scripts, `.github/workflows/*.yml`, `package.json` scripts
in both `platform/` and the repo root, env var references — for
`platform/supabase`) found nothing genuinely depending on it. In
particular, ADR 0007's local-Docker-staging scripts
(`scripts/staging-up.sh`, `scripts/staging-apply-migrations.sh`) were the
one plausible dependent flagged as unaudited in the prior version of this
addendum — read them directly this pass: `staging-up.sh` does
`cd "$(dirname "$0")/.." ` (repo root) before running `supabase start`,
so it always operates against the repo-root `supabase/config.toml`
(`project_id = "fullloopcrm-staging"`), never `platform/supabase/`. Not a
dependent. `scripts/migrate-legacy-to-cli.mjs`'s own `STRAY_CLI_DIR`
constant *was* a dependent (it read the directory as a second source) —
fixed by removing that source entirely (see the next section); the
directory's `existsSync()` guard meant the script would have degraded
gracefully even without that cleanup, but leaving code that reads a
deleted directory was worth removing outright rather than leaving dead
weight. Both of the directory's 2 files were already fully accounted for
in the real baseline before deletion (the RLS file recovered per above; the
`management_applications_resume_optional` file turned out to be a second,
genuinely redundant source of content already converted once from the real
legacy pile — see the duplicate-migration finding below). `git rm -r
platform/supabase/` removed `.gitignore`, `config.toml`, and both
migration files. Going forward: **always run Supabase CLI commands from the
repo root, never from inside `platform/`** — the directory that caused this
in the first place no longer exists to be accidentally recreated by the
same mistake, but the habit is still worth keeping.

### Finding, now fixed (2026-08-01, W9): `scripts/migrate-legacy-to-cli.mjs`'s "safe to re-run" claim was not always true

The script's own docstring claimed re-running it is always safe (skips any
source whose converted output already exists). Verified via `--dry-run`
(read-only, wrote nothing) that this was **false for at least 3 files**:
the RLS gap-closure migration and both `061→063`-renumbered
nycmaid-routing-reconcile migrations. All three were renamed/renumbered at
some point in their git history; the script's `gitAddDates()` helper
(`git log --diff-filter=A`, no rename-detection / `--follow`) failed to
find their real first-add commit in this worktree and silently fell back to
"now" — meaning it computed a **different, wrong timestamp on every run**
for these specific files, which would write a **duplicate** migration file
for content that is already committed under an earlier, correct timestamp.
Root-caused via `git log --follow --diff-filter=A` on each affected source
file, confirming real, stable git history exists that the script's own
(non-`--follow`, directory-wide) query missed.

**Fixed this pass (W9).** `resolveAddDate()` now tries, in order: (1) the
existing fast bulk directory-wide lookup, (2) a per-file `git log --follow
--diff-filter=A` fallback (rename-aware — this is what correctly finds the
two 061→063 files' real 2026-07-12 add date), (3) a `deterministicFallbackDate()`
fallback derived from a SHA-256 hash of the file's own content — used only
when a file has genuinely no git history at all — which replaces the old
`Date.now()` fallback that was the second, distinct trigger for this same
bug class (a file uncommitted at conversion time got a wall-clock
timestamp baked into the baseline; once later committed, the bulk lookup
found a different real date on the next run, and the two never matched).
Neither new code path touches the wall clock, so the same (file, content,
git-history) state now always produces the same output filename. Proven
with `scripts/migrate-legacy-to-cli.test.ts`, including an end-to-end test
that runs the real script's `--dry-run` twice as separate `node`
subprocesses against this repo's actual, unmodified migration pile and
asserts byte-identical stdout (confirmed passing — see that file). This
also let the "design decision" question this addendum previously flagged
resolve itself: a renumbered file's real first-add date is now always its
*true* git-history date (found via `--follow`, whichever name it was under
first), not a filename-current convention — the correct, unambiguous
answer once rename-tracking is actually used.

**One important caveat, not resolved this pass**: fixing the lookup means
the script now computes the *correct* historical timestamps for these 3
files — `20260712150652`/`20260712150653` for the two renumbered files and
`20260728164617` for the RLS file — which **differ** from what is already
committed in `supabase/migrations/` under the old, bug-affected timestamps
(`20260728194627`/`20260728194628`/`20260728194629`). Running the fixed
script for real today would therefore still write 3 *additional* files
(correct content, new version numbers) rather than silently correcting the
existing ones — reconciling the 3 already-committed entries to their
now-known-correct timestamps is a distinct baseline-renumbering decision
(those files may already be referenced elsewhere by exact name) that this
pass deliberately left for whoever runs the actual `supabase migration
repair` baseline-apply step, alongside that same gated action.

### New finding, fixed this pass: a genuine duplicate baseline migration

While auditing `platform/supabase/`'s dependents (previous section),
found that `scripts/migrate-legacy-to-cli.mjs`'s old dual-source design
(reading both `platform/src/lib/migrations/` and the stray
`platform/supabase/migrations/`) had already produced a **real duplicate**
in the committed baseline: `supabase/migrations/20260722145926_management_applications_resume_optional.sql`
(from the real legacy source,
`2026_07_22_management_applications_resume_optional.sql`) and
`supabase/migrations/20260722145927_20260722145537_management_applications_resume_optional.sql`
(from the stray directory's own pre-converted copy of the *same*
migration, `20260722145537_management_applications_resume_optional.sql` —
the file the original ADR text counted as the "one stray already-CLI-formatted
file" / the 158th legacy file). Both contain the identical effective SQL
(`ALTER TABLE management_applications ALTER COLUMN resume_url DROP NOT
NULL;`). Applying `DROP NOT NULL` twice is itself harmless, but two tracked
versions for one real migration is exactly the kind of baseline noise this
whole ADR exists to eliminate, and it was never applied to prod (no risk
in removing it now). **Fixed**: removed
`20260722145927_20260722145537_management_applications_resume_optional.sql`
and its version number from `supabase/BASELINE_VERSIONS.txt`, keeping
`20260722145926` (fuller provenance header, sourced from the real legacy
pile) as canonical. This duplication mechanism cannot recur now that
`platform/supabase/` no longer exists as a second source.

### Correction: `supabase/BASELINE_VERSIONS.txt` did not actually exist

This ADR's own "What was built this pass" table lists this file as an
artifact of the original work. It never existed — the script only ever
printed the same version list to stdout, it never called `writeFileSync` for
this path. Confirmed via `git ls-files` (never tracked) and a fresh disk
check (not present, and `git status` shows no local untracked copy either
— genuinely never generated). **Fixed this pass**: added the missing
`writeFileSync` call to `scripts/migrate-legacy-to-cli.mjs` and generated
`supabase/BASELINE_VERSIONS.txt` for real — but sourced from the **actual
committed contents of `supabase/migrations/`** rather than a live re-run of
the buggy date heuristic above, for the reason explained in that finding.
The file explains this choice inline. **Updated again 2026-08-01 (W9)**:
after removing the duplicate `management_applications` entry (previous
section), the real committed directory now holds 163 files — 162 baseline
+ the 1 still-pending RLS gap-closure file — so
`supabase/BASELINE_VERSIONS.txt` now lists 162 baseline versions. The file
itself documents this latest recount inline.

### Net effect on "the 158 files question"

The core question this ADR and sec-08 exist to answer — did the legacy
migration pile actually get converted and committed — is **yes, confirmed,
and growing correctly**. As of the 2026-08-01 W9 follow-up pass, both
previously-open items from this addendum are now closed: (1) the
disconnected `platform/supabase/` project has been deleted (confirmed
orphaned — nothing in the repo depended on it) and its content fully
accounted for in the real baseline (1 file recovered, 1 file found to be a
genuine duplicate and removed), and (2) the conversion script's
non-deterministic-timestamp bug is fixed and proven idempotent by a real
end-to-end test (`scripts/migrate-legacy-to-cli.test.ts`). What's
genuinely still open: (a) the baseline "applied" repair against prod's
tracking table (unchanged, still gated on Jeff's go), (b) whether to
renumber the 3 already-committed files whose timestamps predate this
pass's fix to their now-known-correct git-history dates (a separate,
deliberate decision — see the caveat in the "safe to re-run" finding
above), and (c) item 4 from the original 2026-08-01 addendum — whether the
prior sec-08 evidence's "linked prod project" claim was ever actually
checking the right project — remains unresolved; this pass made no live
Supabase CLI calls against prod, by design, same constraint as before.
